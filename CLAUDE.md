# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## This is a contest submission — read before touching anything

Manzil is being entered into a competition and winning is the goal, not "it runs." Judging includes Functionality, UI/UX, Demo, AI Integration, and Practical Usefulness — a change that's technically correct but looks unfinished, feels slow, or breaks under a judge's exploratory tapping is a loss condition. Concretely, on this codebase that means:

- **Never fabricate Pakistani curriculum content.** Subject names, chapter titles, pairing-scheme weights — every one of these has already been wrong once from confident guessing (see `src/data/syllabus.ts` header). If you touch syllabus data, verify it against at least 2 independent legitimate sources (or 1 official PCTB/BISE source), explicitly check the source is dated to the *current* curriculum cycle (Class 9 uses different, newer books than Class 10 — a correct-looking source for the wrong year is worse than no source), and never let unverified findings overwrite data that's already confirmed correct. When evidence is thin, say so in the data/comments rather than shipping a confident-sounding placeholder.
- **Never add a single-point-of-failure AI call.** Every Gemini call in `src/lib/gemini.ts` goes through a model chain (`TEXT_CHAIN` / `VISION_CHAIN`) that falls forward on failure — this exists because individual models have genuinely gone down mid-session and because one tier measured ~11x slower on a specific call shape (image + JSON schema) than assumed. A new AI feature bolted on as one bare `fetch` to one model is a regression, not a shortcut. If a call's real-world latency/behavior isn't already proven elsewhere in this file, test it against the live API before trusting it — `tsc` cannot catch a slow model or a bad fallback path.
- **Every failure mode must degrade gracefully, never hard-fail or dead-end.** Typed `GeminiError` + user-facing messages is the existing standard (offline, missing key, API error, unparseable response all have distinct copy). No AI feature should be able to crash a screen or leave the student stuck.
- **`weight` and `difficulty` are load-bearing, not decorative.** They mechanically drive study-time allocation (`planEngine.ts`) and risk-chapter surfacing (`readiness.ts`, threshold `weight >= 4`). A casual edit here silently reshapes every generated plan — treat changes to these fields with the same rigor as changes to the plan engine itself.
- **Run the full regression pass after any data or engine change**, not just `tsc`: `npx expo export --platform android`, then a `tsx` scenario script covering all 6 profile combinations (science-bio/science-cs/arts × class 9/10) exercising `generatePlan()` and `computeReadiness()`. A change that type-checks but produces an empty plan for one profile combo is a shipped bug.
- **Leave the app demoable after every change.** It's judged live on demo, not shipped as a long-running product — never land a change that leaves any screen mid-migration or visibly broken, even temporarily. There's no time pressure, so prefer the higher-quality, more distinctive option over the quick one.

## Project

**Manzil** — mobile AI study planner for Pakistani matric students (Punjab BISE boards, Class 9 & 10). Expo SDK 57 + React Native + TypeScript. Local-first: the app is fully usable with no account and no network, and every screen works offline except the AI calls. The only network traffic is Gemini, plus *opt-in* cloud backup (an account is never required — onboarding has no signup step). Built as a contest entry — the differentiator is real embedded pairing-scheme data + a deterministic plan engine, not another chatbot wrapper.

## Critical constraint

Expo SDK 57 changed significantly. Read the versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing native/config code. Do not assume older-SDK APIs.

## Commands

```bash
npm install                                   # uses .npmrc legacy-peer-deps (required — Radix/react-dom peer conflict)
npx expo start                                # dev; scan QR with Expo Go (Android). Camera features need a real device
npm run web                                    # browser QA (react-native-web) — fastest way to verify UI flows

npx expo export --platform android             # bundle smoke test — catches import/bundling errors tsc misses
npx tsx <script.ts>                            # run a standalone TS script (e.g. plan-engine tests); import via absolute C:/ paths
eas build -p android --profile preview         # cloud build → hosted QR install page (needs Expo login)
# or run .github/workflows/build-apk.yml manually — eas build --local on GH runners, no EAS queue;
# needs only the EXPO_TOKEN repo secret (it also supplies the Gemini key from the EAS "preview" env)
```

There is no test runner configured. Engine logic is verified with throwaway `tsx` scripts (absolute-path imports) + browser walkthrough.

## Setup requirement

AI features need `EXPO_PUBLIC_GEMINI_API_KEY` in `.env` (free key: https://aistudio.google.com/apikey). `.env` is gitignored — never remove that entry, it holds a live key. Without the key, AI screens render but show a graceful "key missing" error. The key ships client-side for the contest build — production would proxy through a server.

Cloud backup additionally needs `EXPO_PUBLIC_SUPABASE_URL` + `EXPO_PUBLIC_SUPABASE_ANON_KEY` in `.env`. Both are optional: without them `isCloudConfigured()` is false, the Cloud Backup card degrades to a "not set up" notice, and file export/import still works. The anon key is safe client-side **only** because `public.backups` has RLS with no `anon` policy; the `service_role` key must never enter the repo.

## Architecture

**Routing** — expo-router, file-based in `app/`. `app/index.tsx` redirects to `/onboarding` or `/(tabs)/today` based on whether a profile exists (after store hydration). `app/(tabs)/` holds the 5 tabs (today, plan, practice, ustaad, progress) with a fully custom `_layout.tsx` tab bar. Full-screen flows (`focus`, `quiz`, `snap`, `grader`, `review`, `breathe`, `dojo`, `settings`, `cloud`, `onboarding`) are top-level routes presented as modals/slides (`breathe` = box-breathing stress-relief tool, launched from Today; `dojo` = theorem proof puzzle, launched from Practice; `settings` = app preferences, vibration toggle, developer bio & interactive study profile editor, launched from top-right of Progress).

**State** — single Zustand store `src/store/useAppStore.ts`, persisted to AsyncStorage under the one key `manzil-store`. Holds `profile`, `plan`, `quizAttempts`, `flashcards`, `chatHistory`, `activeDays`, `vibrationEnabled`. `hydrated` flag gates routing until persistence loads (`onRehydrateStorage`). `computeStreak()` lives here. All app *data* flows through this store — there is no other source of truth (cloud-backup metadata is deliberately a separate store, see below). `BackedUpState`/`BACKED_UP_KEYS` are exported here as a compile-time tripwire: add a field to `AppState` and `backupSchema.ts` fails to build until you decide whether it belongs in a backup.

**The two load-bearing subsystems:**

1. **Syllabus dataset** (`src/data/syllabus.ts`) — the moat. Every subject → chapters for Class 9 (new 2025-26 national-curriculum books) and Class 10 (current PCTB books), Science + Arts groups. Each chapter has `weight` (1-5, board-exam weight derived from official 2026 pairing schemes), `difficulty`, `estMinutes`. `subjectsForProfile(class, group)` is the entry point. `boards.ts` — all 9 Punjab boards share this one dataset. When editing chapter data, `weight` drives the plan engine and readiness scoring — it is not cosmetic.

2. **Plan engine** (`src/lib/planEngine.ts`) — pure/deterministic, no AI in the calendar. `generatePlan(profile)` builds day-by-day sessions across three phases: study pass → revision cycles → past-paper drills. `src/lib/studyTime.ts` is the single source for allowed plans: **120, 180, 240, 360, 420 minutes** (2h, 3h, 4h+, 6h, 7h); onboarding and Plan-tab rebalancing must import it, never duplicate duration lists. **`profile.dailyMinutes` IS the daily target and a hard ceiling — never throttle it.** It decides how fast the first pass completes and therefore how many revision cycles fit; `studyDaysTarget` (~62% of runway) only sets how far content is *compressed* when even a full-capacity pass wouldn't fit. Four invariants, each of which was violated by a shipped bug and is now asserted in `scripts/test-plan-engine.ts` (107 assertions — run it after ANY engine edit): (1) raising daily time must raise the actual daily load — it once saturated at ~90 min so different capacities produced byte-identical plans; (2) session *count* must grow with time — `blockMax = floor(load/2)` with no upper clamp pinned every student at exactly 2 sessions/day; (3) no day may exceed `dailyMinutes` — a `left + 10` tolerance plus sliver-absorption put 101/224 days over budget; (4) no session below `SESSION_MIN`, and no more than 2 consecutive blocks of one subject in a day (`maxSubjectsToday` scales with day length; a flat cap of 3 stacked 8 Urdu blocks back-to-back on a 4-hour day). `splitBlocks()` emits whole-`cap` blocks so they tile a day exactly — equal-sized splitting left a dead ~10-min gap daily. Practice days must also tile the full daily target with 45-minute-max blocks; do not restore a fixed block-count guard (it capped a 7-hour plan at 360 minutes). Revision depth is continuous in confidence (`0.25 + (5-conf)*0.05`); note total revise minutes is deliberately NOT monotonic in confidence, since a confident student finishes the first pass sooner and earns more cycles. **Plan maintenance** — `maintainPlan(plan, profile, today?)` is the single entry point screens call before rendering (today.tsx on mount, settings' Re-balance, backup restore); `repairPlan()` is now just the narrow "only act when overdue" wrapper. It runs `reflowPlan()` then `extendRevision()`. `planNeedsReflow()` is a 4-case decision and the third case is the subtle one: **if nothing is pending today but something was completed today, do NOT reflow** — the student finished their day and has earned rest; only a true *hole* (nothing pending, nothing done today, future work exists) pulls the next work forward. Reflow preserves session identity and existing order (which is what carries `generatePlan`'s subject variety through), and **future** practice drills stay anchored near the exam while still consuming their day's budget — overdue drills are not anchored, they need catching up. `extendRevision()` appends further revision cycles when work would otherwise run out before the practice phase, so a student who studies ahead never hits an idle day. All of these take an injectable `today` so `scripts/test-study-ahead.ts` can run a virtual clock; production always passes the real date.

**Study ahead** — after finishing today, a student may pull forward up to `MAX_DAYS_AHEAD` (3) days, then must rest. It works by *revealing* future sessions on Today, never by re-dating them: re-dating would destroy the information needed to count days-ahead and force a `PlanSession` schema change (and a `backupSchema.ts` migration). `daysAheadUsedToday()` derives the count from `doneAt`, so there is **no new persisted state** and it survives an app restart for free. `completedOn(session)` is the shared definition of "studied on day X" — exported from `planEngine` and used by `useAppStore` for streak credit. **Never key streak/activeDays off `session.date`**: that denies credit for pulled-forward lessons and actively strips today back out of `activeDays` on a day whose own sessions were completed earlier. Verify with `npx tsx scripts/test-study-ahead.ts` (283 assertions; day-by-day simulation of 5 student behaviours × all 6 combos × every daily-time option, re-checking every invariant after every simulated day). Note when reading its output: the daily-budget invariant counts **pending** minutes only — work a student volunteers by pulling ahead is not the engine overbooking them — and the exam date is excluded as the deliberate sink for a backlog larger than the remaining runway. Sessions are dated from `todayISO()` day-index (day 0 = today).

**AI layer** (`src/lib/gemini.ts`) — two ordered model-fallback chains, not one model. `TEXT_CHAIN` = [3.5-flash-lite, 3.1-flash-lite, 3.5-flash], ordered by quota (500/500/20 RPD) — used by `generateQuiz`, `sessionTip`, and `askUstaad` when no image is attached. `VISION_CHAIN` = [3.5-flash, 3.6-flash, 3.5-flash-lite], ordered by speed — Lite tier measured ~11x slower specifically on image+`responseSchema` calls (114s vs ~10-13s) — used by `gradeAnswer`, `cardsFromImage`, and `askUstaad` with an image. `generateChain()` advances to the next model on any `'api'`-kind failure (quota hit, 5xx), so a request only fails once every model in its chain is down; never retries `'key'`/`'offline'`/`'parse'` failures since those recur identically on every model. `APP_CONTEXT` (Pakistan/Matriculation/PCTB framing) is sent as `systemInstruction` on every call — empirically verified to add only ~60 tokens with no safety-filtering or latency effect. Everything feeding app logic uses JSON mode + `responseSchema`, never free-text parsing. Errors throw typed `GeminiError` with `kind: 'offline'|'key'|'api'|'parse'` — screens surface `error.message` directly. `'offline'` is only thrown when the failure text actually looks like lost connectivity (`Network request failed`, `Failed to fetch`, etc.); any other thrown error surfaces its real message as a retryable `'api'` failure instead of being bucketed into a misleading "no internet" — a fetch exception with an unrelated cause (e.g. a bad global patch) was once silently mislabeled offline, which made a real regression invisible. Never widen this back to catching everything as offline. When touching this file, verify against the live API with a `tsx` script (set `EXPO_PUBLIC_GEMINI_API_KEY` in the shell env first) — `tsc` can't catch a wrong model ID or a broken fallback path. Three latency/robustness levers, all measured: (1) `thinkingConfig.thinkingBudget: 0` is forced per-model on the two that accept it — 3.5-flash drops 27s→10s, while 3.6-flash and 3.5-flash-lite 400-reject it (`NO_ZERO_THINKING_MODELS`); (2) every attempt has an `AbortController` timeout (20s text / 140s vision) surfaced as a retryable `'api'` failure so a hung model falls forward instead of hanging; (3) image inputs are downscaled to 1568px longest edge + re-encoded JPEG 0.92 in `src/lib/images.ts` (via `expo-image-manipulator`) before send — lossless at Gemini's internal working resolution but ~5-10x smaller/faster, so don't remove the resize or drop quality below ~0.9.

**Spaced repetition** (`src/lib/fsrs.ts`) — FSRS-lite, fully offline. `reviewCard(card, rating)` grows stability (capped at the 60-day max interval) → next `due` date. A lapse ('again') resets stability to a short relearning value (due tomorrow) regardless of prior maturity — never scale the old stability, which once left just-failed cards scheduled 60 days out. Review queue = cards with `due <= today`.

**Readiness** (`src/lib/readiness.ts`) — `computeReadiness()` blends plan completion (coverage) with quiz mastery, weighted by chapter pairing-scheme weight → per-subject scores, predicted grade band, and `riskChapters` (heavy weight + thin prep). Powers the Progress tab.

**Theorem Dojo** (`src/data/theorems.ts`, `app/dojo.tsx`) — 100% offline interactive proof puzzle titled `Theorem Dojo · مسئلہ ڈوجو (ہندسی ثبوت)` targeting compulsory 8-mark board paper Q9. Dataset in `theorems.ts` contains 10 PCTB theorems (6 Class 10 Q9 theorems from Ch 9 & 12; 4 Class 9 SNC proof results from Ch 9 & 11). `dojo.tsx` implements a 3-phase flow: Read (Given/To Prove/Construction/Hint) → Arrange (tap-to-place shuffled statement+reason steps with undo) → Result (per-step feedback, score & readiness breakdown). Launched from Practice tab (`practice.tsx`) via `DojoIcon`.

**Settings & Study Profile** (`app/settings.tsx`) — App preferences, developer bio (Bilal Murtaza), data management, and interactive Study Profile editor. Allows modifying Student Name, Class Level (Class 9 / Class 10), Study Group (Science Bio / Science CS / Arts), and BISE Board (all 9 Punjab boards in `src/data/boards.ts`). Changing Class Level or Study Group updates `profile` and immediately triggers `setPlan(generatePlan(newProfile))` to regenerate the calendar plan and subject datasets app-wide. Changing BISE Board updates `profile.boardId`, dynamically updating `APP_CONTEXT` for Ustaad AI on every prompt. Haptics toggle updates `vibrationEnabled` in store app-wide. Launched via top-right `SettingsIcon` on Progress tab (`progress.tsx`).

**Cloud backup** (`src/lib/backupSchema.ts`, `cloudBackup.ts`, `supabase.ts`, `backupRestore.ts`, `backupScheduler.ts`, `backupFile.{ts,native.ts,web.ts}`, `src/store/useCloudStore.ts`, `app/cloud.tsx`) — disaster recovery, not multi-device sync: newest upload wins, no per-record merge. Supabase Auth (email+password) + one `public.backups` row per user holding the state as **`text`, not `jsonb`** (jsonb reorders keys and would break the checksum) — schema/RLS in `supabase/schema.sql`. Sync metadata lives in a *separate* store/key (`manzil-cloud-v1`) so it can never travel inside a backup and `resetAll()` can't re-arm it. **Four independent walls stop a fresh install overwriting a good backup**: a reinstall wipes the session (`manzil-auth-v1`), `autoBackup` starts `'off'` and only `armDevice()` flips it (2 call sites, both behind a confirm), `pushBackup()` refuses when `profile === null`, and every non-forced push carries `expectedRev` so a stale device gets 0 rows → `conflict`, which *suspends* auto-backup rather than retrying. `parseBackup()` is the correctness core — untrusted JSON never reaches `setState`; it rebuilds every field from validated values, rejects forward versions outright, and treats a checksum mismatch as a *warning* (JSON round-trips aren't byte-identical for all numbers, so rejecting would dead-end a valid file). Restores write a pre-restore snapshot (`manzil-restore-undo-v1`) *before* mutating, then `repairPlan()` since a restored plan is stale by definition. Scheduler: 45s debounce, 5-min floor, flush on `AppState` background (the one that matters on Android), retry only `offline`/`server`/`rate-limit`. `backupFile` is split by platform extension because **expo-file-system doesn't exist on web** — verified the web bundle contains neither it nor expo-sharing. Free-tier Supabase pauses after 7 idle days; `.github/workflows/supabase-keepalive.yml` pings every ~3 days and fails loudly. Verify with `npx tsx scripts/test-backup-schema.ts` (53 offline assertions, all 6 profile combos + hostile inputs) and `scripts/test-cloud-backup-live.ts` (needs a live project; proves the concurrency wall and cross-user RLS denial — also creates 2 throwaway test accounts, delete from Supabase Auth after). UI surfaces: a "CLOUD BACKUP" card + always-available Export/Import rows in `app/settings.tsx`, and a one-time dismissible `src/components/CloudNudge.tsx` on `today.tsx` shown only after real progress exists (never in onboarding).

**Do not add `react-native-url-polyfill`.** It was tried for Supabase and broke Gemini on native (not web) — `setupURLPolyfill()` unconditionally overwrites `globalThis.URL` with a years-old reimplementation, clobbering Expo SDK 57/RN 0.86's own correct built-in `URL`. RN 0.86 already provides what Supabase needs; the package is a regression here, not a safety net. Full account in `src/lib/supabase.ts`'s header comment.

## Design system

`src/theme/tokens.ts` is the single source for all styling — `color` (Ink & Ivory + Pakistan green; never introduce raw hex in components), `subjectColor` (per-subject identity), `space`, `radius`, `font`, `type`. Two font families: Space Grotesk (UI) + Noto Nastaliq Urdu (`font.urdu`/`urduBold`, used for Urdu accent text throughout). Icons are hand-authored SVGs in `src/components/icons.tsx` — no icon library. Motion is restrained Reanimated (`FadeInDown` entrances, `ProgressRing` animated stroke); haptics on every meaningful tap via `expo-haptics`. Reusable primitives: `Screen`, `PrimaryButton`, `ProgressRing`, `SessionCard`.

## Conventions

- Absolute-from-`src` relative imports (`../../src/lib/...`); no path alias configured.
- ID generation: local `nextId()` counters per file (timestamp + counter) — not uuid.
- Dates are ISO `yyyy-mm-dd` strings throughout; `todayISO()` / `daysUntil()` in `planEngine.ts` are the shared helpers.
- Fonts load in `app/_layout.tsx`; splash held until loaded. Adding a font family means updating both `_layout.tsx` and `tokens.ts`.
- After editing plan/readiness logic, re-run a `tsx` scenario script (225-day + ~20-day crunch + missed-days repair) before trusting it.
- Time-based animations (focus timer, breathe orb) run on a plain JS `setInterval`/`setTimeout` clock, not Reanimated `withTiming` completion callbacks (those proved unreliable across platforms) — the shared value only drives the visual, never the phase/step logic.
