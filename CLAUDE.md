# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## This is a contest submission — read before touching anything

Manzil is being entered into a competition and winning is the goal, not "it runs." Judging includes Functionality, UI/UX, Demo, AI Integration, and Practical Usefulness — a change that's technically correct but looks unfinished, feels slow, or breaks under a judge's exploratory tapping is a loss condition. Concretely, on this codebase that means:

- **Never fabricate Pakistani curriculum content.** Subject names, chapter titles, pairing-scheme weights — every one of these has already been wrong once from confident guessing (see `src/data/syllabus.ts` header). If you touch syllabus data, verify it against at least 2 independent legitimate sources (or 1 official PCTB/BISE source), explicitly check the source is dated to the *current* curriculum cycle (Class 9 uses different, newer books than Class 10 — a correct-looking source for the wrong year is worse than no source), and never let unverified findings overwrite data that's already confirmed correct. When evidence is thin, say so in the data/comments rather than shipping a confident-sounding placeholder.
- **Never add a single-point-of-failure AI call.** Every Gemini call in `src/lib/gemini.ts` goes through a model chain (`TEXT_CHAIN` / `VISION_CHAIN`) that falls forward on failure — this exists because individual models have genuinely gone down mid-session and because one tier measured ~11x slower on a specific call shape (image + JSON schema) than assumed. A new AI feature bolted on as one bare `fetch` to one model is a regression, not a shortcut. If a call's real-world latency/behavior isn't already proven elsewhere in this file, test it against the live API before trusting it — `tsc` cannot catch a slow model or a bad fallback path.
- **Every failure mode must degrade gracefully, never hard-fail or dead-end.** Typed `GeminiError` + user-facing messages is the existing standard (offline, missing key, API error, unparseable response all have distinct copy). No AI feature should be able to crash a screen or leave the student stuck.
- **`weight` and `difficulty` are load-bearing, not decorative.** They mechanically drive study-time allocation (`planEngine.ts`) and risk-chapter surfacing (`readiness.ts`, threshold `weight >= 4`). A casual edit here silently reshapes every generated plan — treat changes to these fields with the same rigor as changes to the plan engine itself.
- **Run the full regression pass after any data or engine change**, not just `tsc`: every suite under Verification suites, plus `npx expo export --platform android`. A change that type-checks but produces an empty plan for one of the 6 profile combos is a shipped bug, and only the suites catch that.
- **When a new suite fails, ask "harness or engine?" before touching engine code.** Wrong assertions have already cost real time here — a budget check that counted voluntary study-ahead work as overbooking, and expectations written against UTC date-slicing. Say plainly when the test was wrong rather than bending the code to a bad assertion.
- **Leave the app demoable after every change.** It's judged live on demo, not shipped as a long-running product — never land a change that leaves any screen mid-migration or visibly broken, even temporarily. There's no time pressure, so prefer the higher-quality, more distinctive option over the quick one.

## Project

**Manzil** — mobile AI study planner for Pakistani matric students (Punjab BISE boards, Class 9 & 10). Expo SDK 57 + React Native + TypeScript. Local-first: the app is fully usable with no account and no network, and every screen works offline except the AI calls. The only network traffic is Gemini, plus *opt-in* cloud backup (an account is never required — onboarding has no signup step). Built as a contest entry — the differentiator is real embedded pairing-scheme data + a deterministic plan engine, not another chatbot wrapper.

Expo SDK 57 changed significantly. Read the versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing native/config code. Do not assume older-SDK APIs.

## Setup requirement

AI features need `EXPO_PUBLIC_GEMINI_API_KEY` in `.env` (free key: https://aistudio.google.com/apikey). `.env` is gitignored — never remove that entry, it holds a live key. Optional `EXPO_PUBLIC_GEMINI_API_KEY_1` … `_10` add keys from other Google accounts; each is an independent free-tier quota bucket, so the pool multiplies the daily ceiling outright (see AI layer for how rotation works). Without any key, AI screens render but show a graceful "key missing" error. Keys ship client-side for the contest build — production would proxy through a server. Every key must also be added to the EAS `preview` environment on expo.dev, or the built APK sees only the ones that are.

The Focus Guard voice pack is already generated and committed, so no key is needed to build or run. Regenerating it needs `ELEVENLABS_API_KEY` in `.env` — deliberately **without** the `EXPO_PUBLIC_` prefix, since that prefix is what inlines a value into the client bundle and a TTS key must never ship to a phone.

Cloud backup additionally needs `EXPO_PUBLIC_SUPABASE_URL` + `EXPO_PUBLIC_SUPABASE_ANON_KEY` in `.env`. Both are optional: without them `isCloudConfigured()` is false, the Cloud Backup card degrades to a "not set up" notice, and file export/import still works. The anon key is safe client-side **only** because `public.backups` has RLS with no `anon` policy; the `service_role` key must never enter the repo.

## Architecture

**Routing** — expo-router, file-based in `app/`. `app/index.tsx` redirects to `/onboarding` or `/(tabs)/today` based on whether a profile exists (after store hydration). `app/(tabs)/` holds the 5 tabs (today, plan, practice, ustaad, progress) with a fully custom `_layout.tsx` tab bar. Full-screen flows (`focus`, `quiz`, `snap`, `grader`, `review`, `breathe`, `dojo`, `motivation`, `settings`, `cloud`, `onboarding`) are top-level routes presented as modals/slides (`breathe` = box-breathing stress-relief tool, launched from Today; `dojo` = theorem proof puzzle, launched from Practice; `motivation` = tap-through Allama Iqbal verses from `src/data/iqbalPoetry.ts`, launched from Today; `settings` = app preferences, vibration toggle, developer bio & interactive study profile editor, launched from top-right of Progress). Every route must survive being opened **without params** — `/quiz` with no chapter once spun forever because a silent early return left it with neither questions nor an error.

**State** — single Zustand store `src/store/useAppStore.ts`, persisted to AsyncStorage under the one key `manzil-store`. Holds `profile`, `plan`, `quizAttempts`, `flashcards`, `chatHistory`, `activeDays`, `vibrationEnabled`, `focusGuardEnabled`, `focusVoiceEnabled`, `focusVoiceId`, `focusVoiceDistracted`, `attentionSpans`. `hydrated` flag gates routing until persistence loads (`onRehydrateStorage`). `computeStreak()` lives here. All app *data* flows through this store — there is no other source of truth (cloud-backup metadata is deliberately a separate store, see below). `BackedUpState`/`BACKED_UP_KEYS` are exported here as a compile-time tripwire: add a field to `AppState` and `backupSchema.ts` fails to build until you decide whether it belongs in a backup.

**The two load-bearing subsystems:**

1. **Syllabus dataset** (`src/data/syllabus.ts`) — the moat. Every subject → chapters for Class 9 (new 2025-26 national-curriculum books) and Class 10 (current PCTB books), Science + Arts groups. Each chapter has `weight` (1-5, board-exam weight derived from official 2026 pairing schemes), `difficulty`, `estMinutes`. `subjectsForProfile(class, group)` is the entry point. `boards.ts` — all 9 Punjab boards share this one dataset. When editing chapter data, `weight` drives the plan engine and readiness scoring — it is not cosmetic.

2. **Plan engine** (`src/lib/planEngine.ts`) — pure/deterministic, no AI in the calendar. `generatePlan(profile)` builds day-by-day sessions across three phases: study pass → revision cycles → past-paper drills. `src/lib/studyTime.ts` is the single source for allowed plans: **120, 180, 240, 360, 420 minutes** (2h, 3h, 4h+, 6h, 7h); onboarding and Plan-tab rebalancing must import it, never duplicate duration lists. **`profile.dailyMinutes` IS the daily target and a hard ceiling — never throttle it.** It decides how fast the first pass completes and therefore how many revision cycles fit; `studyDaysTarget` (~62% of runway) only sets how far content is *compressed* when even a full-capacity pass wouldn't fit. Four invariants, each of which was violated by a shipped bug and is now asserted in `scripts/test-plan-engine.ts` (107 assertions — run it after ANY engine edit): (1) raising daily time must raise the actual daily load — it once saturated at ~90 min so different capacities produced byte-identical plans; (2) session *count* must grow with time — `blockMax = floor(load/2)` with no upper clamp pinned every student at exactly 2 sessions/day; (3) no day may exceed `dailyMinutes` — a `left + 10` tolerance plus sliver-absorption put 101/224 days over budget; (4) no session below `SESSION_MIN`, and no more than 2 consecutive blocks of one subject in a day (`maxSubjectsToday` scales with day length; a flat cap of 3 stacked 8 Urdu blocks back-to-back on a 4-hour day). `splitBlocks()` emits whole-`cap` blocks so they tile a day exactly — equal-sized splitting left a dead ~10-min gap daily. Practice days must also tile the full daily target with 45-minute-max blocks; do not restore a fixed block-count guard (it capped a 7-hour plan at 360 minutes). Revision depth is continuous in confidence (`0.25 + (5-conf)*0.05`); note total revise minutes is deliberately NOT monotonic in confidence, since a confident student finishes the first pass sooner and earns more cycles. **Plan maintenance** — `maintainPlan(plan, profile, today?)` is the single entry point screens call before rendering (today.tsx on mount, settings' Re-balance, backup restore); `repairPlan()` is now just the narrow "only act when overdue" wrapper. It runs `reflowPlan()` then `extendRevision()`. `planNeedsReflow()` is a 4-case decision and the third case is the subtle one: **if nothing is pending today but something was completed today, do NOT reflow** — the student finished their day and has earned rest; only a true *hole* (nothing pending, nothing done today, future work exists) pulls the next work forward. Reflow preserves session identity and existing order (which is what carries `generatePlan`'s subject variety through), and **future** practice drills stay anchored near the exam while still consuming their day's budget — overdue drills are not anchored, they need catching up. `extendRevision()` appends further revision cycles when work would otherwise run out before the practice phase, so a student who studies ahead never hits an idle day. All of these take an injectable `today` so `scripts/test-study-ahead.ts` can run a virtual clock; production always passes the real date.

**Study ahead** — after finishing today, a student may pull forward up to `MAX_DAYS_AHEAD` (3) days, then must rest. It works by *revealing* future sessions on Today, never by re-dating them: re-dating would destroy the information needed to count days-ahead and force a `PlanSession` schema change (and a `backupSchema.ts` migration). `daysAheadUsedToday()` derives the count from `doneAt`, so there is **no new persisted state** and it survives an app restart for free. `completedOn(session)` is the shared definition of "studied on day X" — exported from `planEngine` and used by `useAppStore` for streak credit. **Never key streak/activeDays off `session.date`**: that denies credit for pulled-forward lessons and actively strips today back out of `activeDays` on a day whose own sessions were completed earlier. Verify with `npx tsx scripts/test-study-ahead.ts` (283 assertions; day-by-day simulation of 5 student behaviours × all 6 combos × every daily-time option, re-checking every invariant after every simulated day). Note when reading its output: the daily-budget invariant counts **pending** minutes only — work a student volunteers by pulling ahead is not the engine overbooking them — and the exam date is excluded as the deliberate sink for a backlog larger than the remaining runway. Sessions are dated from `todayISO()` day-index (day 0 = today).

**Dates are LOCAL, never UTC.** `todayISO()`/`localISO()` in `planEngine.ts` are the only date formatters — hand-rolled from `getFullYear/getMonth/getDate`, deliberately **not** `toLocaleDateString('en-CA')`, because Hermes ships partial Intl and an unhonoured locale would return `27/07/2026` and break every string date comparison on device only. `toISOString().slice(0,10)` is banned: it reports UTC, so at UTC+5 the app's day rolled over at 05:00 — a 1 AM session was credited to yesterday, the countdown read a day long, and an FSRS card due "tomorrow" came due that night. `completedOn()` therefore *parses* `doneAt` (a UTC instant) and re-renders it locally rather than slicing it, and `app/quiz.tsx` stamps attempts with `todayISO()` so the store's streak check compares like with like. Verify with `npx tsx scripts/audit-lifecycle.ts` under several zones — `TZ=Asia/Karachi`, `TZ=Pacific/Kiritimati` (UTC+14), `TZ=America/Santiago` (negative offset with DST).

**Two audit suites cover what the others don't.** `npx tsx scripts/audit-study-engine.ts` (186 assertions) asserts the engine *responds* to its inputs — every daily-time step must change daily load, session count and first-pass end date; every confidence step must change revision depth; larger `estMinutes` must earn more time. `npx tsx scripts/audit-lifecycle.ts` (126 assertions) covers the world misbehaving: the exam date passing, clock jumps forward/backward, capacity changed mid-plan, months-old backups, and `maintainPlan` idempotence. Three engine rules they locked down: (1) `fillDays` takes a `blockCap` and re-splits when folding a remainder would exceed it — merging blindly produced measured 78-minute "focused" blocks; (2) when the compressed first pass cannot fit the study window (`mustTriage`), chapters are queued **heaviest-weight first** instead of syllabus order, since truncation is unavoidable but *which* chapters get dropped is a choice — this took heavy-chapter coverage on a 7-day runway from 17/32 to 23/32; (3) once `examDate` has passed, `reflowPlan` drops both the exam clamp and the `examDay` bound, because clamping pins outstanding work onto a past date and strands it permanently.

**`rebalancePlan()` — not `generatePlan()` — is what a daily-time change calls.** Regenerating applies the new pace but wipes every completed session and resets readiness to zero; reflowing re-spreads only pending work and keeps history. It also re-tiles *future* practice days (`retilePractice`), which `reflowPlan` anchors and would otherwise leave holding the old capacity's 420-minute drill days. Switching class/group still regenerates (the syllabi share no chapter IDs) and so is gated behind a confirm naming how many completed sessions are lost.

**AI layer** (`src/lib/gemini.ts`) — fallback runs on **two axes**: model chains and an API-key pool. `generateChain()` iterates **models outer, keys inner**, and which axis advances depends on why the attempt failed (`GeminiError.retry.scope`, an internal hint screens ignore): a **429 rotates the key on the same model** (fresh project quota, identical latency — the case the pool exists for), while a **5xx/timeout/unusable body rotates the model** (a down model is down for every key; grinding all keys through it just buys N timeouts). Models-outer is load-bearing, not stylistic: keys-outer would spend key A's ~114s vision last resort before key B's ~10s first choice. The key pool is `EXPO_PUBLIC_GEMINI_API_KEY` plus `_1`…`_10`, each **written out as a literal `process.env.X` dot-access** — Expo inlines these at build time by static string replacement, so `process.env[\`..._${n}\`]` compiles, type-checks, and finds nothing at runtime; a loop here is a silent outage. Adding an 11th key means adding a line. Keys are trimmed + deduped (same key in two slots would fake redundancy while sharing one bucket), and a key Google *rejects* is retired for the session individually — one typo'd key must never take Ustaad down, so `'key'` only surfaces when the whole pool is rejected. Per-(key, model) cooldowns with exponential backoff (1 min → 1 h) skip known-exhausted pairs, are **in-memory only** (a persisted cooldown could outlive its quota reset and sideline a good key with no way to clear it), and can never themselves cause a refusal — if every pair is cooling, one honest attempt runs with cooldowns ignored. The key travels in an `x-goog-api-key` **header, never a `?key=` query param**, since error strings are rendered straight to the student; `redact()` is the backstop. The per-(key, model) cooldown map key joins its two parts with ` `, written as an **escape sequence, never a raw NUL byte** — a literal NUL in the source makes git classify this file as binary, so every diff to the most security-sensitive file in the repo renders as `Binary files differ` and becomes invisible to review. `geminiKeyPool()` feeds a Settings row showing the resolved key count — without it, a key added to `.env`/expo.dev that didn't register is invisible. Verify with `npx tsx scripts/test-gemini-keypool.ts` (25 assertions: live header auth + rejected-key body shape, then fault-injected 429/503/offline routing asserted as exact `model/key` call sequences). `TEXT_CHAIN` = [3.5-flash-lite, 3.1-flash-lite, 3.5-flash], ordered by quota (500/500/20 RPD) — used by `generateQuiz`, `sessionTip`, and `askUstaad` when no image is attached. `VISION_CHAIN` = [3.5-flash, 3.6-flash, 3.5-flash-lite], ordered by speed — Lite tier measured ~11x slower specifically on image+`responseSchema` calls (114s vs ~10-13s) — used by `gradeAnswer`, `cardsFromImage`, and `askUstaad` with an image. `generateChain()` advances to the next model on any `'api'`-kind failure (quota hit, 5xx), so a request only fails once every model in its chain is down; never retries `'key'`/`'offline'`/`'parse'` failures since those recur identically on every model. `APP_CONTEXT` (Pakistan/Matriculation/PCTB framing) is sent as `systemInstruction` on every call — empirically verified to add only ~60 tokens with no safety-filtering or latency effect. Everything feeding app logic uses JSON mode + `responseSchema`, never free-text parsing. Errors throw typed `GeminiError` with `kind: 'offline'|'key'|'api'|'parse'` — screens surface `error.message` directly. `'offline'` is only thrown when the failure text actually looks like lost connectivity (`Network request failed`, `Failed to fetch`, etc.); any other thrown error surfaces its real message as a retryable `'api'` failure instead of being bucketed into a misleading "no internet" — a fetch exception with an unrelated cause (e.g. a bad global patch) was once silently mislabeled offline, which made a real regression invisible. Never widen this back to catching everything as offline. When touching this file, verify against the live API with a `tsx` script (set `EXPO_PUBLIC_GEMINI_API_KEY` in the shell env first) — `tsc` can't catch a wrong model ID or a broken fallback path. Three latency/robustness levers, all measured: (1) `thinkingConfig.thinkingBudget: 0` is forced per-model on the two that accept it — 3.5-flash drops 27s→10s, while 3.6-flash and 3.5-flash-lite 400-reject it (`NO_ZERO_THINKING_MODELS`); (2) every attempt has an `AbortController` timeout (20s text / 140s vision) surfaced as a retryable `'api'` failure so a hung model falls forward instead of hanging; (3) image inputs are downscaled to 1568px longest edge + re-encoded JPEG 0.92 in `src/lib/images.ts` (via `expo-image-manipulator`) before send — lossless at Gemini's internal working resolution but ~5-10x smaller/faster, so don't remove the resize or drop quality below ~0.9.

**Focus Guard** (`src/lib/focusGuard/`, `app/focus.tsx`) — on-device attention tracking during a study session, via ML Kit face detection through `react-native-vision-camera` + `react-native-vision-camera-face-detector`. **The design pivot: a student revising from a book looks DOWN AT THE BOOK, not at the phone** — "eyes on screen" is the wrong signal (it usually means scrolling), so what's measured is presence, orientation *relative to the student's own calibrated baseline*, and stability. `calibrate()` captures that baseline over 5s and **refuses to run** (returning a typed failure with student-facing copy) rather than guessing; that failure is **terminal, never self-retrying** — it used to leave `baseline` null so every later frame re-ran calibration and re-spoke the failure line ~3x/sec (the "clash of voices" in a dark room), so recovery is now the student tapping "Try again" (`retryCalibration`) — which is what makes it work at a desk, on a bed, on the floor or on a charpai. `stateMachine.ts` is **pure and device-free**: no state ever changes on a single frame, every transition needs dwell time, and hysteresis is asymmetric (4-6s to leave focus, 1.5s to return) so the student always gets the benefit of the doubt. Three rules are load-bearing: (1) **a detected face outranks the light sensor, and darkness may only ever explain a MISSING face** — `classifyInstant` checks `!s.face` first, and only then lets luma decide between `unreliable` (blackout) and `no-face` (they left). This ordering was originally the reverse, so a low reading could veto a face the camera saw perfectly and Focus Guard refused to run in a plainly lit room (reported on a Samsung A55, 2026-07-28). The cause is that luma is NOT frame brightness: it is the ambient sensor on the **front of the phone** (`expo-sensors`, ~lux/100), which collapses when the student leans over the handset or the lamp is behind them, and is simply absent on devices without one. The load-shedding protection is fully preserved because it only ever mattered when the face was already gone — a black empty room is still `uncertain`, never "walked away", this app's most likely false positive in Pakistan. `minLuma` is **0.04 (~4 lux)**, down from 0.12: its only remaining job is separating a true blackout from an empty lit room. (2) `uncertain` time is **excluded from the score's denominator, never counted as distraction** — when the model can't see, it abstains; a useful side effect is that covering the camera earns nothing rather than faking focus. (3) Drowsiness requires eyes shut *and* low motion *and* an absolute near-frontal pose, because ML Kit's eye classifier is unreliable off-frontal — so it silently switches off at a book-reading angle, and rocking while reciting from memory is never called sleep (`memorisationMode` disables it outright). `glance` counts as focus: thinking is not distraction. Camera binding is platform-split (`camera.native.tsx` / `camera.web.tsx` / `camera.tsx`, same pattern as `backupFile`) and every native import is lazily `require`d inside try/catch, so a dev client built before these packages degrade to "unavailable" instead of white-screening. Verify with `npx tsx scripts/test-focus-guard.ts` (146 assertions replaying synthetic traces for every scenario — book reading, glance storms, load-shedding, reciting, occlusion, a sibling passing, gaming the camera). **The suite is mutation-tested**: restoring the old luma-before-face ordering must produce exactly 2 failures (the dim-reader differential and its score assertion). Privacy is a hard constraint, not a preference: no frame is stored, written or transmitted; only ~6 numbers per sample exist; `focusGuardEnabled` defaults **false** and `backupSchema` treats anything other than a literal `true` as off, so a restored backup can never switch a camera on. `recommendedSessionMinutes()` feeds measured attention span back into the Plan tab (median of the recent window, clamped to the engine's 20-60 block range) — the loop that keeps this from being a gimmick. **Requires a rebuilt dev client**; `android.permissions` in app.json carries CAMERA because VisionCamera 5 ships no Expo config plugin and its manifest declares only `uses-feature`. **Not yet verified on real hardware** — detection accuracy in a real room, battery cost over a full session, low-end-device performance, and the ~4 lux darkness threshold are all still unmeasured.

**Focus Guard voice** (`src/lib/focusGuard/voice/`) — **pre-rendered clips, never runtime TTS.** The voice surface is 21 fixed lines, so a TTS call at runtime would buy nothing and cost model latency + a network round trip + a shipped API key + silence during load-shedding; a bundled file plays in ~0 ms, offline, forever. `lines.ts` is the manifest (exact text + the five `FOCUS_VOICES`), `scripts/generate-voice.ts` is the **only vendor-specific code in the repo** — swapping to Azure means replacing `synthesize()` and re-running it, with no app change. That script also **rewrites `assets.ts`**, because Metro resolves asset `require()` statically (same trap as Expo's `EXPO_PUBLIC_*` inlining): a computed path bundles nothing, so every clip needs a literal require, and generating the table is what makes manifest/bundle drift impossible. `ELEVENLABS_API_KEY` is deliberately **not** `EXPO_PUBLIC_`-prefixed — it must never inline into the client. Pack: 5 voices × 21 lines + 1 synthesised chime = 106 files, ~2.4 MB, verified present in the Android bundle manifest (105 mp3 + 1 wav). `cues.ts` is **pure**: it maps a state/phase *transition* (never a state — `away` persists for minutes and must speak once) to a cue, and speaks ONLY at calibration, away/return, drowsy, and — **behind its own opt-in** (`focusVoiceDistracted`, default off) — sustained distraction. `focused`/`glance`/`uncertain` stay silent unconditionally. The distraction line is the one most likely to embarrass a student sharing a room, hence the separate consent and copy written so an overhearing sibling learns nothing; it is also the only cue triggerable on demand, which makes it what you switch on to test or demo the voice. **`return` requires actually seeing them back**: `away -> uncertain` is not a return, and firing one there was half a spam loop, since a dark room flickers away/uncertain and alternated "Timer paused"/"Welcome back". `lastSpokeAt` is nullable, not `0`: a 0 sentinel made the cooldown depend on `now` being a huge absolute timestamp and silently swallowed the first cue of every session under any session-relative clock. Playback resolves through **expo-asset before expo-audio**, because handing a bundled `require()` straight to `useAudioPlayer` works in dev and **fails silently in release builds** (expo#33665, expo#40448). Audio ducks rather than interrupts (students study to recitation) and respects the silent switch. **Exactly one utterance plays at a time**, enforced in `player.native.ts` (`stopSpeaking()` before every cue) rather than in the cue layer — nothing tracked the previous player, so two cues arriving close together simply played over each other, and the guard belongs where no future caller can bypass it. The pending post-chime line is registered as live too, so a stop landing in the 420 ms gap cancels a line that has not started yet. `focusVoiceEnabled` is a **separate opt-in from the camera**, default off, and `focusVoiceId` is validated on restore against `isKnownVoice`. Free-tier ElevenLabs terms require the attribution line in Settings → About. Verify with `scripts/test-focus-guard.ts` (146 assertions; cue routing, cooldown, non-repeating variants, and every manifest file asserted present **on disk** — the generated asset table can't be imported by Node since it requires .mp3).

**Answer grader mark bands** (`gradeAnswer` in `gemini.ts`, `app/grader.tsx`) — the chip row is **2 / 5 / 8 / 10**; there is no 3-mark question in this paper pattern and short questions carry 2, so the original `[3, 5, 8]` offered a size that does not exist and omitted two that do. Passing the number through was never enough: the prompt hard-coded "2-3 strengths, 2-4 improvements" whatever the size, which on a 2-mark answer forces the model to invent faults to fill a quota, and nothing told it that **brevity is correct** at 2 marks, so a complete short answer could be marked down for being short. `MARK_BANDS` therefore brief the examiner per size and scale those counts, banded by **range not exact value** so any mark number still gets sane guidance. `questionBandLabel()` is exported so the chip caption and the prompt come from one table and cannot drift. Verified live (`npx tsx scripts/test-grader-bands.ts`, 16 assertions): the same two-line answer scores **2/2 at 2 marks with 1 improvement** and **3/10 at 10 marks with 4** — the band is genuinely honoured, not just interpolated into a string.

**Spaced repetition** (`src/lib/fsrs.ts`) — FSRS-lite, fully offline. `reviewCard(card, rating)` grows stability (capped at the 60-day max interval) → next `due` date. A lapse ('again') resets stability to a short relearning value (due tomorrow) regardless of prior maturity — never scale the old stability, which once left just-failed cards scheduled 60 days out. Review queue = cards with `due <= today`.

**Readiness** (`src/lib/readiness.ts`) — `computeReadiness()` blends plan completion (coverage) with quiz mastery, weighted by chapter pairing-scheme weight → per-subject scores, predicted grade band, and `riskChapters` (heavy weight + thin prep). Powers the Progress tab.

**Theorem Dojo** (`src/data/theorems.ts`, `app/dojo.tsx`) — 100% offline interactive proof puzzle titled `Theorem Dojo · مسئلہ ڈوجو (ہندسی ثبوت)` targeting compulsory 8-mark board paper Q9. Dataset in `theorems.ts` contains 10 PCTB theorems (6 Class 10 Q9 theorems from Ch 9 & 12; 4 Class 9 SNC proof results from Ch 9 & 11). `dojo.tsx` implements a 3-phase flow: Read (Given/To Prove/Construction/Hint) → Arrange (tap-to-place shuffled statement+reason steps with undo) → Result (per-step feedback, score & readiness breakdown). Launched from Practice tab (`practice.tsx`) via `DojoIcon`.

**Settings & Study Profile** (`app/settings.tsx`) — preferences, developer bio (Bilal Murtaza), data management, and the Study Profile editor (Student Name, Class Level, Study Group, BISE Board from `src/data/boards.ts`). Class/Group changes go through `confirmRegenerate()`, which names how many completed sessions will be lost and can be cancelled — it used to fire on a single tap and silently wipe all progress, which is precisely the "breaks under a judge's exploratory tapping" loss condition. Board change updates `profile.boardId` → `APP_CONTEXT` on every Ustaad prompt. Also hosts the haptics toggle, the **Focus Guard opt-in** (default off; disables itself with an explanatory line when unsupported), and read-only diagnostics: Ustaad AI key count and data counts. Launched via top-right `SettingsIcon` on Progress.

**Cloud backup** (`src/lib/backupSchema.ts`, `cloudBackup.ts`, `supabase.ts`, `backupRestore.ts`, `backupScheduler.ts`, `backupFile.{ts,native.ts,web.ts}`, `src/store/useCloudStore.ts`, `app/cloud.tsx`) — disaster recovery, not multi-device sync: newest upload wins, no per-record merge. Supabase Auth (email+password) + one `public.backups` row per user holding the state as **`text`, not `jsonb`** (jsonb reorders keys and would break the checksum) — schema/RLS in `supabase/schema.sql`. Sync metadata lives in a *separate* store/key (`manzil-cloud-v1`) so it can never travel inside a backup and `resetAll()` can't re-arm it. **Four independent walls stop a fresh install overwriting a good backup**: a reinstall wipes the session (`manzil-auth-v1`), `autoBackup` starts `'off'` and only `armDevice()` flips it (2 call sites, both behind a confirm), `pushBackup()` refuses when `profile === null`, and every non-forced push carries `expectedRev` so a stale device gets 0 rows → `conflict`, which *suspends* auto-backup rather than retrying. `parseBackup()` is the correctness core — untrusted JSON never reaches `setState`; it rebuilds every field from validated values, rejects forward versions outright, and treats a checksum mismatch as a *warning* (JSON round-trips aren't byte-identical for all numbers, so rejecting would dead-end a valid file). Restores write a pre-restore snapshot (`manzil-restore-undo-v1`) *before* mutating, then `repairPlan()` since a restored plan is stale by definition. Scheduler: 45s debounce, 5-min floor, flush on `AppState` background (the one that matters on Android), retry only `offline`/`server`/`rate-limit`. `backupFile` is split by platform extension because **expo-file-system doesn't exist on web** — verified the web bundle contains neither it nor expo-sharing. Free-tier Supabase pauses after 7 idle days; `.github/workflows/supabase-keepalive.yml` pings every ~3 days and fails loudly. Verify with `npx tsx scripts/test-backup-schema.ts` (60 offline assertions, all 6 profile combos + hostile inputs) and `scripts/test-cloud-backup-live.ts` (proves the concurrency wall and cross-user RLS denial). UI surfaces: a "CLOUD BACKUP" card + always-available Export/Import rows in `app/settings.tsx`, and a one-time dismissible `src/components/CloudNudge.tsx` on `today.tsx` shown only after real progress exists (never in onboarding).

**Do not add `react-native-url-polyfill`.** It was tried for Supabase and broke Gemini on native (not web) — `setupURLPolyfill()` unconditionally overwrites `globalThis.URL` with a years-old reimplementation, clobbering Expo SDK 57/RN 0.86's own correct built-in `URL`. RN 0.86 already provides what Supabase needs; the package is a regression here, not a safety net. Full account in `src/lib/supabase.ts`'s header comment.

## Design system

`src/theme/tokens.ts` is the single source for all styling — `color` (Ink & Ivory + Pakistan green; never introduce raw hex in components), `subjectColor` (per-subject identity), `space`, `radius`, `font`, `type`. Two font families: Space Grotesk (UI) + Noto Nastaliq Urdu (`font.urdu`/`urduBold`, used for Urdu accent text throughout). Icons are hand-authored SVGs in `src/components/icons.tsx` — no icon library. Motion is restrained Reanimated (`FadeInDown` entrances, `ProgressRing` animated stroke); haptics on every meaningful tap via `expo-haptics`. Reusable primitives: `Screen`, `PrimaryButton`, `ProgressRing`, `SessionCard`.

## Conventions

- Absolute-from-`src` relative imports (`../../src/lib/...`); no path alias configured.
- ID generation: local `nextId()` counters per file (timestamp + counter) — not uuid.
- Dates are ISO `yyyy-mm-dd` strings throughout; `todayISO()` / `localISO()` / `daysUntil()` in `planEngine.ts` are the only helpers (see "Dates are LOCAL").
- Fonts load in `app/_layout.tsx`; splash held until loaded. Adding a font family means updating both `_layout.tsx` and `tokens.ts`.
- Native modules are lazily `require`d inside try/catch (see `focusGuard/camera.native.tsx`), so a dev client built before a package was added degrades instead of white-screening.
- Time-based animations (focus timer, breathe orb) run on a plain JS `setInterval`/`setTimeout` clock, not Reanimated `withTiming` completion callbacks (those proved unreliable across platforms) — the shared value only drives the visual, never the phase/step logic.
